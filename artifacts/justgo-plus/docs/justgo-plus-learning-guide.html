1. Product overview

JustGo Plus is a Malaysian highway companion concept. The supplied reference screens show account entry and registration, ANPR identity onboarding, toll-related transactions, monthly e-Invoice verification, and account settings. This implementation recreates those user-facing surfaces in Expo / React Native and provides useful local interactions for learning and demonstration.

The main navigation contains Home, Transactions, e-Invoice, and Me. Supporting flows include Login/Register, profile editing, vehicle management, Touch ’n Go/RFID list management, identity information, payment-method information, password-change information, notifications, and informational pages.

Know what is real in this build. You can edit and save local demo profile fields, vehicles, and card/tag labels. You cannot sign in to a real PLUSMiles account, verify a phone or identity, register an account with a server, enter card payment details, or retrieve real toll transactions.

3. MVVM architecture in this project

MVVM means Model–View–ViewModel. A repository is also used to isolate persistence. This project keeps screen presentation apart from data rules and storage:

Viewapp/ + components/
Displays state and sends user actions.
→
ViewModelviewmodels/
Owns screen state, validation flow, and commands.
→
Modelmodels/
Defines the domain data shapes and defaults.
↔
Repositoryrepositories/
Loads and saves local demo data.

Model — the vocabulary of the app

models/index.ts defines types such as Profile, Vehicle, TollCard, TransactionFilter, Transaction, and the overall AppData. It also defines valid document and nationality options, the initial sample profile, and a default filter.

export interface Vehicle { id: string; plate: string; make: string; model: string; color: string; createdAt: number; }

The type describes the shape; it does not save a vehicle or decide how a form should behave. Keeping this vocabulary centralized reduces accidental disagreement between views and view-models.

View — what the user sees

app/ contains file-based route screens, including app/(tabs)/index.tsx and app/(tabs)/transactions.tsx. components/ contains reusable visual pieces like shared UI elements, SVG artwork, auth forms, and confirmation sheets. A view should render the state it receives and call a view-model action when a user taps or types; it should not know AsyncStorage key names.

ViewModel — screen behavior and presentation state

viewmodels/ exposes hooks such as useLoginViewModel, useRegisterViewModel, useProfileProgress, useTransactionsViewModel, and entity form hooks. The app-wide AppContext.tsx provides shared data and commands such as profile updates and vehicle/card CRUD. View-models translate user events into domain operations and offer convenient, screen-ready state.

Repository and services — boundaries around IO and shared rules

repositories/demoRepository.ts wraps AsyncStorage reads, writes, and clearing. The services/ folder contains validation rules, informational content, and haptics. Isolating these makes it easier to replace local demo persistence with an API later without teaching every screen how networking works.

4. Following one user action through the app

Consider changing a vehicle. This demonstrates the intended dependency direction:

  1. The user edits fields in the vehicle form view at app/vehicle-form.tsx.
  2. The screen calls a setter exposed by useVehicleFormViewModel, which stores the current draft and clears field errors as the user corrects them.
  3. On Save, the view-model calls validateVehicle from services/validation.ts.
  4. If validation fails, the view-model returns field errors for the view to render. No data is saved.
  5. If valid, the view-model calls saveVehicle from AppContext.
  6. The context creates or updates an immutable AppData snapshot and asks demoRepository.save to persist it.
  7. Context state updates cause subscribed views—such as Home progress and the vehicle list—to rerender.
// Simplified teaching model, not a copy of the app's exact function View: onPress={() => viewModel.save()} ViewModel: validate draft; if valid, call app command Context: create the next AppData snapshot Repository: AsyncStorage.setItem(key, JSON.stringify(snapshot))

This separation is useful because screen layout can change without rewriting persistence, and persistence can change without copying storage logic into every screen.

6. State and local persistence

Two kinds of state

  • Shared app state: AppData is managed by AppProvider and exposed through useApp(). It includes signed-in demo mode, language, profile, vehicles, cards, and transaction filters.
  • Temporary screen state: drafts, selected tabs, open sheets, error messages, and registration fields live inside the relevant screen/view-model and do not all become persisted app data.

Persistence lifecycle

  1. When the provider mounts, it loads the stored JSON through demoRepository.load().
  2. The repository merges loaded fields with defaults to handle partially missing profile/filter data. It also treats an absent or unsupported language value as English for older saved records.
  3. A command creates the next state and persists it through AsyncStorage.setItem.
  4. “Delete local demo data” clears this app’s key and initializes a fresh signed-out demo state. The selected language is preserved.

The storage key is versioned (justgo-plus/demo-data/v1), a useful pattern when the shape of saved data may change. AsyncStorage stores a serialized snapshot on one device; it does not synchronize across users or phones and does not provide server backups.

Language setting and translations

English is the default. AppData.language uses en for English and ms for Bahasa Melayu. The user opens Me → General → Language. app/language.tsx calls setLanguage() in viewmodels/AppContext.tsx; the update changes shared context and is saved with the same AsyncStorage snapshot.

constants/i18n.ts stores Malay text using the English UI text as its lookup key. components/LocalizedText.tsx reads the selected language and translates visible text. Shared fields also translate their placeholders. If a key has no Malay entry, the English text remains visible. Add translations there when you add or change UI copy. The app uses this internal table; it does not follow the iOS system language automatically.

Data safety distinction: AsyncStorage is appropriate here for sample profile fields, local demo lists, and the language choice. It is not a secure vault for passwords, identity numbers, access tokens, or payment details. The current app explicitly avoids persisting these sensitive values.

7. Forms, validation, and honest unavailable states

Validation helpers in services/validation.ts return a typed map of field names to messages. The form view-model stores the draft and errors, invokes a validator on submit, and asks the view to display the returned message. Examples include email format, Malaysian mobile format, a 12-digit MyKad number, vehicle plate shape, and demo TNG/RFID number formats.

Validation is a convenience and data-quality check, not identity verification or security. In a real service, a trusted backend must validate again, enforce rate limits, and call the authoritative identity/payment systems.

Login actions validate input, then display an explicit “not connected” notice. They do not send an OTP, verify an identity, or grant access to a real JustGo account. Email password input is cleared instead of being stored. Registration checks name, document format, and consent before moving to account details; submitting still tells the user that registration and identity services are not connected. The ID number is neither sent to a server nor stored in AsyncStorage.

8. Design system and visual assets

constants/colors.ts centralizes the screenshot-inspired color palette, typography names, corner radius, and the px() scaling helper. Reference measurements use a 472-pixel source width and scale to a 393-point layout. Screens consume shared token values rather than inventing independent colors and font choices. A small shared creator credit—“This app was created by Afiq”—is rendered in the primary header regions across authentication, the tab screens, and supporting routes.

components/Art.tsx uses SVG vector shapes for the brand-like marks, symbols, bottom navigation icons, and illustrations. This keeps assets scalable, but vector redraws are approximations of branded artwork; the reference screenshots remain the authority for visual comparison. app.json supplies app name, icon, scheme, orientation, and router settings. Root setup preserves Inter font loading and hides the splash screen after fonts resolve (or fail).

The app also accounts for native safe areas and a web preview. The custom tab bar intentionally uses the dark reference design rather than the operating system’s default liquid-glass appearance.

For any future API feature, define the API contract first in the shared OpenAPI specification, regenerate the shared client, implement a backend route, and have the mobile view-model use the generated client. Keep secrets on the server; never bake service credentials into the app bundle.

10. A practical learning path

  1. Start at the root: read app/_layout.tsx and identify each provider and the router stack.
  2. Trace a screen: read the Transactions route, then useTransactionsViewModel.ts, then the filter types in models/index.ts. Note what lives in the view versus the view-model.
  3. Trace persistence: follow setFilter in AppContext.tsx into demoRepository.save(). Try changing a filter and restarting the preview to see how local storage behaves.
  4. Trace a form: inspect vehicle form screen, its view-model, and validateVehicle(). See how typed field errors are rendered.
  5. Make a safe UI change: alter a shared token in constants/colors.ts and observe the screens that use it.
  6. Add a small feature: define its model first, decide whether state is temporary or persistent, implement repository/context behavior if needed, create a view-model action, then add the view and route.
  7. Keep demo boundaries: never turn a local button into a fake “verified” or “paid” status. Add real provider integration and server confirmation before presenting those states as true.

Example: adding a favorite item

  1. Add a typed Favorite model or add a favorites collection to AppData.
  2. Choose whether favorite state belongs on device or must sync between signed-in devices. For a local prototype, store it via the repository; for production sync, use an authenticated API.
  3. Add a command in the context to add/remove a favorite immutably.
  4. Expose a view-model action and derived state such as isFavorite.
  5. Render an accessible button in the view and persist only non-sensitive fields.
  6. Test first-launch, reload, add/remove, and empty states.

11. Glossary

ComponentA reusable UI building block rendered by React.
RouteA screen address mapped from a file by Expo Router.
HookA React function such as useApp() that reads shared state or behavior.
ContextA React mechanism for sharing values across a component tree without threading props through every layer.
Immutable updateCreating a new object/array to represent changed state rather than mutating the old snapshot in place.
RepositoryA boundary hiding how data is loaded/saved, allowing the storage mechanism to be replaced.
AsyncStorageAsynchronous local key/value storage on a device; not a secure credential store.
Safe areaThe part of the screen not obscured by a notch, status bar, or home indicator.
ANPRAutomatic Number Plate Recognition; the app screenshots describe toll payment onboarding involving ANPR.
APIA defined interface through which the mobile app and a server exchange requests and responses.
MVVMModel–View–ViewModel: separates domain data, presentation, and screen behavior.
